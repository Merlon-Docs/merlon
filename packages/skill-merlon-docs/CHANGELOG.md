# @merlon-docs/skill-merlon-docs

## 1.0.0-draft.0

### Major Changes

- 5ab62e8: This is the 1.0 draft of Merlon Docs. The CLI, the core library, the presets and the Agent Skills publish as `1.0.0-draft.N` prereleases under the npm `draft` tag. Install the newest draft with `npm install @merlon-docs/merlon-docs-cli@draft`. The interfaces can still change between drafts. 1.0.0 is the first release with a stability guarantee, and from 1.0.0 on a breaking change needs a major version.

### Minor Changes

- 9bc05cd: The `merlon-docs` skill is now the only skill to install. The helper skills (`mdcp-getting-started`, `mdcp-doc-only`, `mdcp-design-architecture`, `mdcp-feature-level`, `mdcp-ux`) are folded into it as workflow files under `references/workflows/`, and the skill picks the workflow for each task from a routing table. Invoke it as `/merlon-docs` with the task in plain words, such as `/merlon-docs help me get started`.

  A new doc-review workflow reviews the docs as a set, using `merlon review` for the mechanical pass, and the skill offers it on its own when a sprawl trigger matches (several new shards, a crowded guide index, a rule found in two places). For projects whose docs change every week, it also recommends a weekly routine that reviews each guide on its own; for one-off projects it says the routine is not needed.

  If you installed a helper skill, remove it and install `merlon-docs` alone: `npx skills add Merlon-Docs/merlon --skill merlon-docs`. The helper skills are no longer published.

- 58452d2: MDCP (MarkDown Context Protocol) is now Merlon Docs. The packages publish as `@merlon-docs/merlon-docs-cli`, `@merlon-docs/merlon-docs-core` and `@merlon-docs/merlon-docs-presets`, and the CLI command is `merlon`. The Agent Skill installs as `merlon-docs` with `npx skills add Merlon-Docs/merlon --skill merlon-docs`, and the archetypes are `merlon-docs-arch-*`.

  The config file is `merlon.config.json`. Until 2.0.0, a CLI run that finds `mdcp.config.json` and no `merlon.config.json` upgrades the project itself. It writes the config to `merlon.config.json` with `protocolVersion` renamed to `standardVersion`, deletes `mdcp.config.json` and prints a notice. The illustrative-paths marker is `<!-- merlon-paths: illustrative -->`, and the former `mdcp-paths` spelling still works until 2.0.0.

  The Vale style is `MerlonDocs`, so a rule reads `MerlonDocs.DatedClaim`. Compiled outputs carry `<!-- merlon-shard: … -->` markers. In the core API the config types are `MerlonConfig`, `MerlonConfigInput` and `MerlonConfigSchema`, and the `Mdcp*` names stay as deprecated aliases until 2.0.0.

  To migrate a project, install the new packages, run any `merlon` command once to upgrade the config file, and change `MDCP` to `MerlonDocs` in `.vale.ini`, in `<!-- vale MDCP.… -->` comments and in the `StylesPath` link to the presets.

- cc41907: The getting-started workflow and the first-feature tutorial no longer end with a call to action. The tutorial's Closing CTA section asked the agent to invite the user to star the repository and join an outside community, and the workflow ran that section after the tutorial and after a skip. The tutorial now ends at its last phase, and when the user skips it the workflow hands off to the matching day-to-day workflow. The getting-started eval fixture drops the Closing CTA assertions and keeps every other one.

### Patch Changes

- 9bc05cd: Use "compiled guide" for the file compile writes for one guide, and keep "monolith" for the optional top-level `outputFile`. The `merlon compile` help text now reads "Stitch shards into compiled guides". The `ignoreGuides` type docs now say that links to a listed guide's shards keep source `.md` paths instead of `#slug` targets in the file that holds the target guide. The `standaloneGuides` schema description now says a standalone guide doesn't get compile output of its own. The `merlon shard` help text now reads "Split a source document into shards (md-tree)". The `merlon-docs` skill's context guardrails tell agents not to load whole compiled output (a compiled guide or the monolith). The product docs site archetype skill now says "one large file" instead of "monolith" for an oversized authoring tree.
- 9bc05cd: The getting-started workflow now settles Vale before the first `merlon check`. When Vale is installed and the user has not asked for prose linting, it writes a placeholder `.vale.ini` in the docs root and says prose linting is off. A fresh scaffold now passes `merlon check` instead of failing on the missing file.
- 258e7e8: The feature-level workflow's Docs First step points at What belongs where in `SKILL.md` for the guide table and the placement test, in place of a separate three-row table and a separate test that turned on whether a consumer could do without the shard. `SKILL.md` and the specification it follows ask whether consumers of the product need the shard.
- 9bc05cd: Workflows no longer stop at intake when nobody can answer. The skill takes `WORK_ITEM` and the other intake values from the request and the repository. When a value is still missing, it states the default it picked and carries on. It still waits when the user asked for a plan first, and before a destructive step, a change of scope, or input only the user can give.
- 9bc05cd: The **Current docs only** principle gives each kind of old text one destination. The history behind a rule or constraint that still holds, such as an erratum or how things worked before the rule, moves to an ADR, or the repo's equivalent decision record, that the shard or standalone guide links. The shard or standalone guide keeps today's reason in one present-tense sentence and does not link the incident log or ticket behind the change, which stays in the tracker as **No temp info or backlogs** requires. The rule applies over a repo-local convention that asks for that history inline. Text that only describes removed behavior is deleted, and its consumer notice goes in the changeset. The wrap-up steps of the doc-only, feature-level, design-architecture and ux workflows state the same split, and design-architecture marks a superseded ADR as superseded instead of deleting it. The staff engineer review lens checks the split. The ADR writes each date on its own, because the `MerlonDocs.DatedClaim` Vale rule flags a date after `as of` or `until`. The consolidation playbook applies the split to a dated or "used to" passage and keeps the rule on for ADRs. The rule goes off only for a record that is dated by design, such as a research record. Such a record opts out inline, or in a `.vale.ini` path section placed after every section that matches the same files.

  A new **Removing or renaming a concept** section in `SKILL.md` gives the steps for a change that removes or renames a component, flag or command in the product, or a term in the docs. The steps also apply when a change, such as an ADR written after the removal, finds docs that still describe a component, flag or command that the product no longer has. Docs describe a concept for as long as the product has it, so a design that only plans a removal leaves them unchanged, and the change that makes the removal runs the steps. From the repository root, the agent runs `git grep --untracked -n -i -F` with one `-e` per spelling over the quoted pathspec `'*.md'`. Git matches that pathspec in every directory, which brings standalone guides and unregistered guides into the search along with the docs root. A standalone guide or agent instruction file in another extension, such as `.mdc`, gets a pathspec of its own. The command leaves out `-w`. Each spelling then also finds a plural that only adds letters, such as `workers` for `worker`. A plural that changes the ending, such as `proxies` for `proxy`, gets its own `-e`, and a short word that needs `-w` moves out of the command into a second command of its own. For a name of two or more words, an extra `-e` for its most distinctive word finds a mention that a line break splits. The consolidation playbook explains what each option matches, and its move-or-rename step runs the same command. The agent then runs the repo's docs check, its `docs:check` script or `merlon check`, with `lint.paths.severity` set to `warn` for that run when the repo leaves it unset or `off`. It fixes the hits that refer to the old concept in the same change and puts each search command and the files it hit in the commit message. Those fixes belong to the change in every workflow, standalone guides outside the docs root included. The doc-only workflow's scope names standalone guides beside `docs/**` shards. Historical records such as ADRs, CHANGELOGs and research records keep their mentions, and so do pending changesets, vendor-managed skill installs and test fixtures. A removed or renamed concept is also a sprawl trigger, and the feature-level, doc-only, ux and doc-review workflows point to the new section. The routing table sends an architecture, RFC or ADR request to the design-architecture workflow before or after the code change, and that workflow checks the code for each component, flag or command that the design removes or renames. When the code still has it, the docs that describe it stay, and the plan or reply says that the feature-level change that makes the removal follows the section. A superseded design shard retires only when the code does not follow it. When the code no longer has it, or the design shards rename or drop a term, the workflow follows the section itself.

  When the skill recommends the weekly review routine, the repo's contributor docs state what starts each run and what evidence each run leaves, including a run that doesn't find anything. The trigger is a CI cron workflow, a scheduled task, or a named role that the docs assign the run to as a duty. A schedule alone is no trigger, and neither is a team or role that the docs name without assigning it the run. The docs state only a trigger the repo has. Until it has one, the skill tells the user what to set up and leaves the routine out of the docs, or labels the routine advisory with the role that may run it and what a run leaves behind. The evidence outlasts CI log retention, such as a comment on a standing tracker item, and an advisory routine doesn't need a record of a run that finds nothing. In any project, a documented cadence with no trigger is removed or labeled advisory in the same way. One with a trigger but no stated evidence gains the record its runs leave, or the skill tells the user what to add when runs leave none. The staff engineer review lens asks the same of any recurring task that the docs promise.

- 9bc05cd: `SKILL.md` gains a table for requests that come with a document layout attached, such as one file for everything, a legacy doc extended in place, or every copy of a rule patched. The skill keeps the shard structure and lists in its reply each request it did not follow literally.
- 05c27dc: The skill's text follows the docs it repeats. The doc-only, design-architecture, feature-level and ux workflows no longer branch from `main`. They update the integration branch that the delivery conventions at `WORK_ITEM_LOOKUP` name, or the default branch when they name none, and branch from it.

  The shard single responsibility principle in `SKILL.md` says a shard serves one audience, the word `references/shard-responsibility.md` uses, where it said one audience tier.

  The routing diagram in `SKILL.md` sends design-architecture work to `docs/features/` and `docs/features/adr/`, the directories that workflow writes to, where it said `docs/features/` including the system specs and ADRs.

  The What belongs where table in `SKILL.md` uses the wording of the specification's default guide layout. The features row keeps out code walkthroughs. The client row holds consumer value and usage of the product, including install and configuration. The developer row adds workflow, tracker integration and releases. The weekly review routine is recommended when docs changed in most weeks of the last month, and most weeks means commits in at least three different weeks of the docs directory's git log for the last four weeks. The old text counted code changes too and gave the git log count as an example.

  The doc-only workflow's writing step puts intent, contracts and acceptance criteria in shards, not code dumps, and allows a link to a source file only as evidence for a claim, which the compile hook for code evidence rewrites to a line fragment.   The getting-started workflow seeds the domain terms the inclusion bar allows, the phrasing its workflow shard uses.

- 9bc05cd: The skill description now says to use it for feature, bugfix, documentation and design work in any repository with a `docs/` folder or `merlon.config.json`, even when the request never mentions docs. Plain requests such as "add a `--format` option" now load the skill.
- 01b6d2b: The config key for the version of the Merlon Docs standard is now `standardVersion`, defaulting to `1.0.0-draft.0` with the 1.0 draft line (replacing the former `0.5.0.0` label and `protocolVersion` name). A config that still sets `protocolVersion` keeps working until 2.0.0: `loadConfig` and the new `parseConfig` copy its value to `standardVersion`, and they fail when the two keys hold different values. A parsed config still has `protocolVersion`, set to the same value. The JSON schema marks `protocolVersion` as deprecated.

  The copyright line in each license now reads Merlon Docs. Code comments, the JSON schema and the docs now call the specification "the standard". The presets README now refers to the `MerlonDocs` Vale style, which the rename had missed.
