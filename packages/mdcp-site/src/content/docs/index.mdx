Add the skill to any repository that runs an agent host with [Agent Skills](https://agentskills.io) support:

```bash
npx skills add betsalel-williamson/mdcp --skill mdcp
```

## The foundation under your helper skills

Coding agents now pull in skills the way projects pull in libraries. One skill runs brainstorming and planning, another enforces test-driven development, and others handle debugging, code review or frontend design. Each helper makes the agent better at a task, and each one is finished when that task merges.

The project keeps going after the merge. The README, the user guide and the design records still have to describe the code as it is now, and no helper skill does that work. Their plans and specs describe a change while it is in flight, then sit unchanged as the code moves on.

MDCP does. It is the guardrail beneath the helpers: whichever skill wrote the change, `mdcp check` runs on the same pull request and fails it when the docs no longer match. Pick helper skills for how your team likes to work. Install MDCP once, and the docs keep matching the code whichever ones you pick.

## What makes it a protocol

<CardGrid>
  <Card title="Open" icon="open-book">
    MIT licensed. The specification and the reference CLI live in one public repository, and the
    protocol version is tracked apart from package releases.
  </Card>
  <Card title="Plain Markdown" icon="document">
    Shards are GitHub Flavored Markdown with no custom syntax. Any editor opens them, and if you
    stop using MDCP you keep ordinary docs.
  </Card>
  <Card title="Enforced in CI" icon="approve-check">
    `mdcp check` turns the protocol's rules into a build step. The check runs on the pull request
    itself, whoever reviews it.
  </Card>
  <Card title="For agents and people" icon="puzzle">
    An agent opens the one shard its task needs, while a person reads the compiled README built from
    that same shard.
  </Card>
</CardGrid>

## How it works

<Steps>

1. **Shard.** Each topic is a small Markdown file in a guide directory under `docs/`. A manifest sets the reading order, and the default layout splits guides by audience.

   ```text
   docs/
   ├── mdcp.config.json
   ├── features/    product capabilities and design records
   ├── client/      install and usage for consumers
   ├── developer/   setup, workflow and releases for contributors
   └── glossary/    one term per shard
   ```

2. **Compile.** `mdcp compile` stitches the shards into the files readers open on GitHub and npm, rewriting cross-links so they resolve in the published location. Compiled files are output, and you edit the shard instead.

   ```bash
   mdcp compile --config docs/mdcp.config.json --docs-root docs
   ```

3. **Check.** `mdcp check` runs in CI. It fails when a link points at a heading that no longer exists, when a compiled file is stale, or when a peer linter you turned on reports a problem.

   ```text
   link: packages/mdcp-cli/README.md:115: dead anchor … (compiled guide "client-cli")

   mdcp check failed:
     - built-in links: 1 issue(s) (see `link:` lines above)
   ```

4. **Keep going.** The `mdcp` skill tells the agent when to update a shard and how. It picks a workflow from the request: bootstrap, docs-only, design, feature, UX or doc review.

</Steps>

## The specification

MDCP 1.0 is a draft. The reference CLI and library lead, and the prose is reconciled against `@bwilliamson/mdcp-core` before the specification is called final. It uses RFC 2119 keywords and defines the default guide layout, the skill workflows and how agents receive context. Wire transport is out of scope.
