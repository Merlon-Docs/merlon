<section class="mdcp-section">

<p class="mdcp-kicker">Why it matters</p>

## Unreliable software is expensive, and missing docs are part of why

<div class="mdcp-lead">
  Software failures cost hundreds of billions to trillions of dollars a year. Documentation isn't
  the only cause. Vulnerabilities, supply chains and technical debt all play a part. But it's the
  cause a team can act on in its next pull request.
</div>

<div class="mdcp-split mdcp-split--text">
  <div>
    There's no substitute for knowing the system. When a project leaves its intent, features and
    operating knowledge unwritten, from the technical parts to the non-technical ones, the software
    is released with gaps: a decision nobody recorded, a workflow only one person knows, a guide
    that still describes a component someone removed.
  </div>
  <div>
    DORA's research doesn't say documentation caused these costs. It finds that documentation
    quality amplifies the other practices a team invests in. MDCP is a keystone AI skill for that
    one cause. It gives the knowledge a place to live that people and agents both read, and it
    checks the links, indexes and compiled files.
  </div>
</div>

</section>

<section class="mdcp-section">

<p class="mdcp-kicker">The problem</p>

## Where docs break when agents edit a repository

<div class="mdcp-lead">
  Code shows what a system does, but not why the team built it that way, and people outside
  engineering can't read it. When agents write much of the change, documentation fails in a few
  familiar ways. Most of them are structural, so a check can catch them.
</div>

<ul class="mdcp-problems">
  <li>
    <h3>One long docs file</h3>
    <div>
      Every change edits the same file, so branches conflict and the table of contents goes stale.
    </div>
    <div class="mdcp-fix">
      Each topic is its own shard. <code>mdcp compile</code> assembles the README or handbook,
      contents included.
    </div>
  </li>
  <li>
    <h3>Guessed links</h3>
    <div>
      Agents write <code>#anchor</code> slugs from memory, and the links break without anyone
      noticing.
    </div>
    <div class="mdcp-fix">
      <code>mdcp check</code> fails CI on a broken link or anchor and names the file and line.
    </div>
  </li>
  <li>
    <h3>Pages nobody indexed</h3>
    <p>A new file is merged, but no guide lists it, so no reader finds it.</p>
    <div class="mdcp-fix">
      Every shard must appear in a guide index or the check fails, which makes adding a page a
      deliberate act.
    </div>
  </li>
  <li>
    <h3>Stale compiled output</h3>
    <div>
      Someone edits the README by hand or forgets to rebuild it, and it stops matching its source.
    </div>
    <div class="mdcp-fix">
      The check fails when a compiled file differs from what its shards produce.
    </div>
  </li>
  <li>
    <h3>The whole handbook in every prompt</h3>
    <p>Pasting every page into each turn spends context on pages the task doesn't need.</p>
    <div class="mdcp-fix">
      An agent following the skill reads only the shards for its task. MDCP doesn't stop it from
      reading more.
    </div>
  </li>
  <li>
    <h3>Intent that never gets written down</h3>
    <p>A decision is made in a pull request or a ticket and is never written into the docs.</p>
    <div class="mdcp-fix">
      The skill tells the agent to update shards in the same change, and a reviewer checks that the
      words match what the team meant.
    </div>
  </li>
</ul>

<div>
  <code>mdcp check</code> covers the structural failures. It doesn't judge whether the prose is
  true. That part rests on the agent following the skill and on human review.
</div>

</section>

<section class="mdcp-section">

<p class="mdcp-kicker">Why every repository needs one</p>

## A keystone among your helper skills

<div class="mdcp-lead">
  Agents pick up helper skills for each task, such as planning, test-driven development or code
  review. Those skills help finish the task in front of them. MDCP looks after what outlasts the
  task, from the intent behind a feature to how the system is built and operated.
</div>

<ol class="mdcp-steps">
  <li>
    <h3>The agent writes</h3>
    <div>
      The <code>mdcp</code> skill tells the agent which shards a change touches and to update them
      in the same change as the code.
    </div>
  </li>
  <li>
    <h3>A person confirms intent</h3>
    <div>
      Shards are small and change in the same pull request, so a reviewer can check that the docs
      say what the team meant.
    </div>
  </li>
  <li>
    <h3>The CLI checks structure</h3>
    <div>
      <code>mdcp check</code> fails CI on broken links and anchors, missing files, unindexed shards
      and stale compiled files. It doesn't judge whether the prose is true.
    </div>
  </li>
</ol>

</section>

<section class="mdcp-section">

<p class="mdcp-kicker">How it works</p>

## Organize docs once, write for every reader

<div class="mdcp-split">
  <div>
    <div class="mdcp-lead">
      Docs live in a <code>docs/</code> folder as small Markdown files called shards, one topic per
      file. Guides list which shards they include, and <code>mdcp compile</code> assembles each
      guide into the README or handbook its reader opens.
    </div>
    <div>
      A new perspective is a new guide over existing shards. Drafting a customer guide from the same
      shards, or reviewing the whole set, takes a language model little time.
    </div>
  </div>
  <pre class="mdcp-tree" role="region" aria-label="Example docs folder" tabindex="0">
    <code>
      {`docs/
├── mdcp.config.json
├── features/    what the product does and why
├── client/      install and usage
├── developer/   setup and workflow
└── glossary/    one term per file`}
    </code>
  </pre>
</div>

<ul class="mdcp-features">
  <li>
    <h3>Focused feature work</h3>
    <p>An agent building a feature reads only the few shards that describe it.</p>
  </li>
  <li>
    <h3>Ready for retrieval</h3>
    <p>Small, single-topic files are a natural first step toward retrieval-augmented generation.</p>
  </li>
  <li>
    <h3>Plain Markdown</h3>
    <div>
      GitHub Flavored Markdown with no custom syntax. Stop using MDCP and you keep ordinary docs.
    </div>
  </li>
  <li>
    <h3>Open</h3>
    <p>MIT licensed. The specification and the reference CLI share one public repository.</p>
  </li>
</ul>

<p class="mdcp-kicker">Who it's for</p>

## Beyond engineering docs

<div class="mdcp-lead">
  The default layout is built for software, but the same shards and guides work for any team that
  writes its knowledge down as text, as long as the source isn't a canvas.
</div>

<ul class="mdcp-chips" aria-label="Teams">
  <li>Engineering</li>
  <li>Product</li>
  <li>Design and UX</li>
  <li>Marketing</li>
  <li>Sales</li>
  <li>Support</li>
</ul>

<div>
  Teams that design in a canvas tool such as Figma still have reasoning that reads better as text,
  such as the decision behind a layout or the steps a user follows through a flow. Kept as shards,
  that text becomes the raw material for a help center or user documentation site.

<p class="mdcp-kicker">Status</p>

## Where MDCP stands

<div class="mdcp-panel">

MDCP is an early project, built by one maintainer with help from a colleague. It's useful today and still being refined. On a [repository where agents wrote every commit](./concepts/protocol/research/field-report-automated-repository/), the structural checks held: every shard was indexed and no broken internal link reached trunk. The agents produced useful documentation, but it sprawled, with seven shards past 300 lines and one guide still describing a removed component. A person used the skill's doc-review workflow to reorganize it. That gap between structure and meaning is what current work on the protocol and the skill targets.

</div>

<dl class="mdcp-evidence mdcp-evidence--three" aria-label="Measured results">
  <div>
    <dt>0</dt>
    <dd>broken links between shards reached trunk in 50 commits on a 75-shard repository</dd>
  </div>
  <div>
    <dt>94 of 94</dt>
    <dd>shards indexed on a repository where agents wrote all of its 1,450 or so commits</dd>
  </div>
  <div>
    <dt>1.3 s</dt>

  </div>
</dl>

<p class="mdcp-kicker">FAQ</p>

## Questions

<div class="mdcp-faq">

<details>
  <summary>Does MDCP keep docs in sync with the code automatically?</summary>

Not by itself. The CLI checks that docs refer to each other and to files correctly. Whether the prose still matches the code depends on an agent following the skill and a person reviewing the change.

</details>

<details>
  <summary>Does MDCP replace my other skills?</summary>

No. Helper skills plan, write and review code. MDCP records what the project needs to remember about that code. Install both.

</details>

<details>
  <summary>Do I need the agent skill to use it?</summary>

No. The `mdcp` CLI compiles and checks docs on its own, in CI or locally. The skill adds the instructions an agent follows to update shards as it works.

</details>

<details>
  <summary>Which agents does it work with?</summary>

Any host that supports [Agent Skills](https://agentskills.io), including Claude Code, Cursor and GitHub Copilot.

</details>

<details>
  <summary>Is MDCP an MCP server?</summary>

No. The Model Context Protocol connects agents to live tools and data. MDCP works on files in your repository and runs in CI. See [scope and positioning](./concepts/protocol/01-scope-and-positioning/).

</details>

</div>
