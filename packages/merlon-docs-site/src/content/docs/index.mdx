<section class="merlon-section">

<p class="merlon-kicker">Why it matters</p>

## Unreliable software is costly, and missing documentation is the fix you can ship next

<div class="merlon-lead">
  Software failures cost hundreds of billions to trillions of dollars a year. Security
  vulnerabilities, fragile supply chains, and technical debt all drive those losses, but missing
  documentation is the risk factor your team can address in its next pull request.
</div>

<div class="merlon-split merlon-split--text">
  <div>
    When engineers leave design decisions and runbooks unwritten, teams ship with blind spots: a
    constraint nobody recorded, an operational step only one person knows, or a guide that still
    describes a removed component. That gap slows down releases, incident response, and onboarding.
  </div>
  <div>
    DORA research finds that documentation quality amplifies the other engineering practices a team
    invests in. Merlon Docs gives human engineers and AI coding agents a shared home for system
    knowledge in git. <code>merlon compile</code> builds single-file guides for review, and{' '}
    <code>merlon check</code> validates indexes, links, and paths in CI while engineers and agents
    verify that the prose stays accurate.
  </div>
</div>

</section>

<section class="merlon-section">

<p class="merlon-kicker">Who it's for</p>

## For the people who answer for reliability

<div class="merlon-lead">
  If you're responsible for the platform, the team's delivery, quality or the skills your agents
  load, Merlon Docs gives you a documentation practice you can set as policy instead of hoping for
  it.
</div>

<ul class="merlon-features">
  <li>
    <h3>Platform and DevOps leads</h3>
    <div>
      Add one check to the pipeline you already run. Broken links, unindexed pages and stale
      compiled docs fail the build.
    </div>
  </li>
  <li>
    <h3>Engineering and technical managers</h3>
    <div>
      When intent is written down and reviewed with each change, you can learn what the system does
      without asking the one person who remembers.
    </div>
  </li>
  <li>
    <h3>QA and reliability engineers</h3>
    <div>
      Acceptance criteria and known constraints live in shards next to the code, where a test or a
      review can point at them.
    </div>
  </li>
  <li>
    <h3>Owners of the AI skill stack</h3>
    <div>
      One skill, beside your planning and review skills, that tells every agent to update the docs
      it touches.
    </div>
  </li>
</ul>

### Make it policy

<ol class="merlon-steps">
  <li>
    <h3>Install the skill</h3>
    <div>
      Add <code>npx skills add Merlon-Docs/merlon --skill merlon-docs</code> to each repository's
      agent setup.
    </div>
  </li>
  <li>
    <h3>Require the check</h3>
    <div>
      Make <code>merlon check</code> a required CI job, so broken docs block a merge like a failing
      test.
    </div>
  </li>
  <li>
    <h3>Review docs with code</h3>
    <div>Ask reviewers to read the shard diff beside the code diff in each pull request.</div>
  </li>
</ol>

<div class="merlon-aside">

Already the person who writes things down? Merlon Docs gives your notes a structure that agents and the next reader can use, and a check that keeps the links working. The same shards suit product, design and support teams that keep their knowledge as text.

</div>

</section>

<section class="merlon-section">

<p class="merlon-kicker">The problem</p>

## Where docs break when agents edit a repository

<div class="merlon-lead">
  Code shows what a system does, but not why the team built it that way, and people outside
  engineering can't read it. When agents write much of the change, documentation fails in a few
  familiar ways. Most of them are structural, so a check can catch them.
</div>

<ul class="merlon-problems">
  <li>
    <h3>One long docs file</h3>
    <div>
      Every change edits the same file, so branches conflict and the table of contents goes stale.
    </div>
    <div class="merlon-fix">
      Each topic is its own shard. <code>merlon compile</code> assembles the README or handbook,
      contents included.
    </div>
  </li>
  <li>
    <h3>Guessed links</h3>
    <div>
      Agents write <code>#anchor</code> slugs from memory, and the links break without anyone
      noticing.
    </div>
    <div class="merlon-fix">
      <code>merlon check</code> fails CI on a broken link or anchor and names the file and line.
    </div>
  </li>
  <li>
    <h3>Pages nobody indexed</h3>
    <p>A new file is merged, but no guide lists it, so no reader finds it.</p>
    <div class="merlon-fix">
      Every shard must appear in a guide index or the check fails, which makes adding a page a
      deliberate act.
    </div>
  </li>
  <li>
    <h3>Stale compiled output</h3>
    <div>
      Someone edits the README by hand or forgets to rebuild it, and it stops matching its source.
    </div>
    <div class="merlon-fix">
      The check fails when a compiled file differs from what its shards produce.
    </div>
  </li>
  <li>
    <h3>The whole handbook in every prompt</h3>
    <p>Pasting every page into each turn spends context on pages the task doesn't need.</p>
    <div class="merlon-fix">
      An agent following the skill reads only the shards for its task. Merlon Docs doesn't stop it
      from reading more.
    </div>
  </li>
  <li>
    <h3>Intent that never gets written down</h3>
    <p>A decision is made in a pull request or a ticket and is never written into the docs.</p>
    <div class="merlon-fix">
      The skill tells the agent to update shards in the same change, and a reviewer checks that the
      words match what the team meant.
    </div>
  </li>
</ul>

<div>
  <code>merlon check</code> covers the structural failures. It doesn't judge whether the prose is
  true. That part rests on the agent following the skill and on human review.
</div>

</section>

<section class="merlon-section">

<p class="merlon-kicker">Why every repository needs one</p>

## A keystone among your helper skills

<div class="merlon-lead">
  Agents pick up helper skills for each task, such as planning, test-driven development, or code
  review. Those skills help finish the task in front of them. Merlon Docs looks after what outlasts
  the task, from the intent behind a feature to how the team builds and operates the system.
</div>

<ol class="merlon-steps">
  <li>
    <h3>The agent writes</h3>
    <div>
      The <code>merlon-docs</code> skill tells the agent which shards a change touches and to update
      them in the same change as the code.
    </div>
  </li>
  <li>
    <h3>A person confirms intent</h3>
    <div>
      Shards are small and change in the same pull request, so a reviewer can check that the docs
      say what the team meant.
    </div>
  </li>
  <li>
    <h3>The CLI checks structure</h3>
    <div>
      <code>merlon check</code> fails CI on broken links and anchors, missing files, unindexed
      shards, and stale compiled files. It doesn't judge whether the prose is true.
    </div>
  </li>
</ol>

</section>

<section class="merlon-section">

<p class="merlon-kicker">Foundational AI skills</p>

## Built for software repositories, in the same family as LLM Wiki and aDNA

<div class="merlon-lead">
  Task skills help an agent finish one job, like writing a test, fixing a bug, or reviewing a diff.
  Foundational AI skills manage the durable context that outlasts a single chat session.{' '}
  <a href="https://github.com/alainbrown/skills/tree/main/skills/llm-wiki">LLM Wiki</a>,{' '}
  <a href="https://adna.network/reference/specification/">aDNA</a>, and Merlon Docs all solve that
  problem with plain Markdown files, but they target different scopes.
</div>

<div class="merlon-split merlon-split--text">
  <div>
    LLM Wiki and aDNA organize general knowledge across any domain. LLM Wiki runs a compounding wiki
    loop (init, ingest, query, and lint), while aDNA structures a broad knowledge vault into what,
    who, and how directories across any subject.
  </div>
  <div>
    Merlon Docs is purpose-built for software projects maintained in git. Shards sit next to source
    code, <code>merlon compile</code> stitches them into single-file guides for review, and{' '}
    <code>merlon check</code> validates links against real repository files, directories, and
    headings in CI.
  </div>
</div>

<ul class="merlon-features">
  <li>
    <h3>LLM Wiki</h3>
    <div>
      Compounding general-knowledge wiki. Agents initialize a wiki, ingest external sources, query
      across sessions, and lint wiki pages for consistency.
    </div>
  </li>
  <li>
    <h3>aDNA</h3>
    <div>
      General-purpose knowledge vault organized into what, who, and how directories. It pairs folder
      instructions, domain notes, and procedural skills across any subject.
    </div>
  </li>
  <li>
    <h3>Merlon Docs</h3>
    <div>
      Purpose-built for software repositories. Shards hold specs, decision records, runbooks, and
      glossaries next to code, compiled with <code>merlon compile</code> and gated in CI by{' '}
      <code>merlon check</code>.
    </div>
  </li>
  <li>
    <h3>Wired into AGENTS.md</h3>
    <div>
      Point <code>AGENTS.md</code> at the <code>merlon-docs</code> skill so coding agents read and
      update the relevant shards in the same pull request as the code, for engineers who maintain
      the system over the long haul.
    </div>
  </li>
</ul>

<section class="merlon-section">

<p class="merlon-kicker">How it works</p>

## Organize docs once, write for every reader

<div class="merlon-split">
  <div>
    <div class="merlon-lead">
      Docs live in a <code>docs/</code> folder as small Markdown files called shards, one topic per
      file. Guides list which shards they include, and <code>merlon compile</code> assembles each
      guide into the README or handbook its reader opens.
    </div>
    <div>
      A new perspective is a new guide over existing shards. Drafting a customer guide from the same
      shards, or reviewing the whole set, takes a language model little time.
    </div>
  </div>
  <pre class="merlon-tree" role="region" aria-label="Example docs folder" tabindex="0">
    <code>
      {`docs/
├── merlon.config.json
├── features/    what the product does and why
├── client/      install and usage
├── developer/   setup and workflow
└── glossary/    one term per file`}
    </code>
  </pre>
</div>

<ul class="merlon-features">
  <li>
    <h3>Focused feature work</h3>
    <p>An agent building a feature reads only the few shards that describe it.</p>
  </li>
  <li>
    <h3>Ready for retrieval</h3>
    <p>Small, single-topic files are a natural first step toward retrieval-augmented generation.</p>
  </li>
  <li>
    <h3>Plain Markdown</h3>
    <div>
      GitHub Flavored Markdown with no custom syntax. Stop using Merlon Docs and you keep ordinary
      docs.
    </div>
  </li>
  <li>
    <h3>Open</h3>
    <p>MIT licensed. The specification and the reference CLI share one public repository.</p>
  </li>
</ul>

<p class="merlon-kicker">Status</p>

## Where Merlon Docs stands

<div class="merlon-panel">

Merlon Docs is an early project, built by one maintainer with help from a colleague. It is useful today and under active refinement. On a [repository where agents wrote every commit](./concepts/system/research/field-report-automated-repository/), the structural checks held: guide manifests indexed every shard and no broken internal link reached trunk. The agents produced useful documentation, but it sprawled, with seven shards past 300 lines and one guide still describing a removed component. A person used the skill's doc-review workflow to reorganize it. That gap between structure and meaning is what current work on the system and the skill targets.

</div>

<dl class="merlon-evidence merlon-evidence--three" aria-label="Measured results">
  <div>
    <dt>0</dt>
    <dd>broken links between shards reached trunk in 50 commits on a 75-shard repository</dd>
  </div>
  <div>
    <dt>94 of 94</dt>
    <dd>shards indexed on a repository where agents wrote all of its 1,450 or so commits</dd>
  </div>
  <div>

  </div>

<p class="merlon-kicker">FAQ</p>

## Questions

<div class="merlon-faq">

<details>
  <summary>Does Merlon Docs keep docs in sync with the code automatically?</summary>

Not by itself. The CLI checks that docs refer to each other and to files correctly. Whether the prose still matches the code depends on an agent following the skill and a person reviewing the change.

</details>

<details>
  <summary>Does Merlon Docs replace my other skills?</summary>

No. Helper skills plan, write, and review code. Merlon Docs records what the project needs to remember about that code. Install both.

</details>

<details>
  <summary>Do I need the agent skill to use it?</summary>

No. The `merlon` CLI compiles and checks docs on its own in CI or locally. The skill adds the instructions an agent follows to update shards as it works.

</details>

<details>
  <summary>Which agents does it work with?</summary>

Any host that supports [Agent Skills](https://agentskills.io), including Claude Code, Cursor, and GitHub Copilot.

</details>

<details>
  <summary>Is Merlon Docs an MCP server?</summary>

No. The Model Context Protocol connects agents to live tools and data. Merlon Docs works on files in your repository and runs in CI. See [scope and positioning](./concepts/system/01-scope-and-positioning/).

</details>

</div>
