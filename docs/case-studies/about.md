# About case studies

A case study follows one project that adopted Merlon Docs. It covers three things: the process the project follows, the outcomes it has reached, and the exploratory results, which are the things tried along the way whether or not they worked.

Each case study opens with its status. A case study that is **in progress** follows work that is still under way: its figures are interim readings, each update gives the date and commit it read, and nothing in it is reported as a final result. Once the work ends, the case study is marked **complete** and, like a [research record](../features/system/research/about-research-records.md), keeps the observation as written. A later look at the same project is a new case study that links back to it. Unlike a research record, a case study names its project, because the project's owner published the work and chose to have it written up.

Paths in a case study name files in the project's own repository, not in this one, so each case study shard opts out of path resolution, and its links to those files are pinned to the commit it was written from. Every figure in a case study says where it came from, such as a file in the project's repository, a pull request, or a command anyone can run again, and states its main caveat. A figure describes that project at the time it was read. Under [Benefit claims and evidence](../features/system/benefit-claims-and-evidence.md#figures-from-records-and-studies), it supports at most a Tier B claim and is never stated as a general outcome.

To propose a case study, open an issue as [Versions and feedback](../repo-readme/versions-and-feedback.md) describes.
