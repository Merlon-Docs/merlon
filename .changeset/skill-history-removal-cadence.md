The **Current docs only** principle gives each kind of old text one destination. The history behind a rule or constraint that still holds, such as an erratum or how things worked before the rule, moves to an ADR, or the repo's equivalent decision record, that the shard or standalone guide links. The shard or standalone guide keeps today's reason in one present-tense sentence and does not link the incident log or ticket behind the change, which stays in the tracker as **No temp info or backlogs** requires. The rule applies over a repo-local convention that asks for that history inline. Text that only describes removed behavior is deleted, and its consumer notice goes in the changeset. The wrap-up steps of the doc-only, feature-level, design-architecture and ux workflows state the same split, and design-architecture marks a superseded ADR as superseded instead of deleting it. The staff engineer review lens checks the split. The ADR writes each date on its own, because the `MDCP.DatedClaim` Vale rule flags a date after `as of` or `until`. The consolidation playbook applies the split to a dated or "used to" passage and keeps the rule on for ADRs. The rule goes off only for a record that is dated by design, such as a research record. Such a record opts out inline, or in a `.vale.ini` path section placed after every section that matches the same files.

A new **Removing or renaming a concept** section in `SKILL.md` gives the steps for a change that removes or renames a component, flag or command in the product, or a term in the docs. The steps also apply when a change, such as an ADR written after the removal, finds docs that still describe a component, flag or command that the product no longer has. Docs describe a concept for as long as the product has it, so a design that only plans a removal leaves them unchanged, and the change that makes the removal runs the steps. From the repository root, the agent runs `git grep --untracked -n -i -F` with one `-e` per spelling over the quoted pathspec `'*.md'`. Git matches that pathspec in every directory, which brings standalone guides and unregistered guides into the search along with the docs root. A standalone guide or agent instruction file in another extension, such as `.mdc`, gets a pathspec of its own. The command leaves out `-w`. Each spelling then also finds a plural that only adds letters, such as `workers` for `worker`. A plural that changes the ending, such as `proxies` for `proxy`, gets its own `-e`, and a short word that needs `-w` moves out of the command into a second command of its own. For a name of two or more words, an extra `-e` for its most distinctive word finds a mention that a line break splits. The consolidation playbook explains what each option matches, and its move-or-rename step runs the same command. The agent then runs the repo's docs check, its `docs:check` script or `mdcp check`, with `lint.paths.severity` set to `warn` for that run when the repo leaves it unset or `off`. It fixes the hits that refer to the old concept in the same change and puts each search command and the files it hit in the commit message. Those fixes belong to the change in every workflow, standalone guides outside the docs root included. The doc-only workflow's scope names standalone guides beside `docs/**` shards. Historical records such as ADRs, CHANGELOGs and research records keep their mentions, and so do pending changesets, vendor-managed skill installs and test fixtures. A removed or renamed concept is also a sprawl trigger, and the feature-level, doc-only, ux and doc-review workflows point to the new section. The routing table sends an architecture, RFC or ADR request to the design-architecture workflow before or after the code change, and that workflow checks the code for each component, flag or command that the design removes or renames. When the code still has it, the docs that describe it stay, and the plan or reply says that the feature-level change that makes the removal follows the section. A superseded design shard retires only when the code does not follow it. When the code no longer has it, or the design shards rename or drop a term, the workflow follows the section itself.

When the skill recommends the weekly review routine, the repo's contributor docs state what starts each run and what evidence each run leaves, including a run that doesn't find anything. The trigger is a CI cron workflow, a scheduled task, or a named role that the docs assign the run to as a duty. A schedule alone is no trigger, and neither is a team or role that the docs name without assigning it the run. The docs state only a trigger the repo has. Until it has one, the skill tells the user what to set up and leaves the routine out of the docs, or labels the routine advisory with the role that may run it and what a run leaves behind. The evidence outlasts CI log retention, such as a comment on a standing tracker item, and an advisory routine doesn't need a record of a run that finds nothing. In any project, a documented cadence with no trigger is removed or labeled advisory in the same way. One with a trigger but no stated evidence gains the record its runs leave, or the skill tells the user what to add when runs leave none. The staff engineer review lens asks the same of any recurring task that the docs promise.
